# 001. 라우팅 라이브러리와 URL 구조

## 상황

앱의 플로우가 여러 화면에 걸쳐 있고(공연 목록 → 상세 → 좌석 선택 → 예매 완료),
새로고침 시 같은 화면이 복원되어야 한다는 요구사항이 있다.
이에 따라 라우팅 라이브러리 선택과 URL 구조 결정이 필요했다.

## 검토한 선택지

- **React Router v6**: 가장 널리 쓰이는 라우터. 레퍼런스 풍부. loader/action 패턴 등 부가 기능 있음. 버전 혼재로 예제 혼란 있음.
- **TanStack Router**: TypeScript 기반 search params 타입 추론이 장점. 레퍼런스 적음.

## 결정과 이유

**React Router v6** 선택.

TanStack Router의 타입 안전 search params가 매력적이지만,
URL에 복잡한 값을 담지 않기로 판단했기 때문에 그 장점을 쓸 자리가 없다.
도구의 장점이 내 문제와 만나지 않으면 선택 근거가 안 된다.

또한 지금 목적이 직접 코드를 짜는 훈련이라 막혔을 때 검색으로 뚫리는 게 중요하다.
2차에서 대용량 렌더링과 실시간을 다뤄야 하니 학습 시간을 거기에 써야 한다.

loader 패턴 사용 여부는 지금 확정하지 않는다.
서버 상태 관리 도구 선택 시 역할이 겹칠 수 있어, 그때 같이 판단한다.
현재는 `<Link>`, `useNavigate`, `useParams` 수준으로만 시작한다.

---

**URL 구조 결정:**

판단 기준: "새로고침하면 같은 화면이 나와야 하는가."

```
/                       공연 목록
/concerts/:id           공연 상세
/concerts/:id/seats     좌석 선택
/bookings/:bookingId    예매 완료 (확인)
```

- 화면 단위는 URL에 드러낸다. 새로고침으로 같은 화면이 복원되어야 하기 때문이다.
- 내가 고른 좌석 목록은 URL에 담지 않는다. 좌석 선점 정보는 서버가 진실이고,
  URL에 또 담으면 두 곳이 어긋날 수 있다. 그 링크를 남에게 보내도 의미가 없다 — 그 좌석은 내가 잡고 있으니까.
- `/booking/confirm` 대신 `/bookings/:bookingId`를 쓴다.
  confirm은 "막 완료한 순간"에만 의미 있는 URL이라 새로고침 시 근거가 없다.
  bookingId가 있으면 서버에서 언제든 같은 데이터를 가져올 수 있다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

URL에 담아야 할 상태가 계속 늘어나서, search params를 직접 파싱하는 코드가 쌓이기 시작하면
TanStack Router를 안 쓴 판단을 재검토해야 한다.

## 되돌리는 비용

`<Link>`, `useNavigate`, `useParams` 훅이 컴포넌트 안에 직접 쓰이면
라우터를 바꿀 때 컴포넌트를 하나씩 수정해야 한다.
추상화 계층(예: `useAppNavigate` 같은 커스텀 훅)을 두면 교체 비용이 줄지만,
현재는 그 추상화를 도입하지 않았으므로 전면 교체가 필요한 상황이 생길 수 있다.
