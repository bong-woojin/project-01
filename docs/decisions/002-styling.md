# 002. 스타일링 방식

## 상황

React 컴포넌트 스타일링 방식을 결정해야 했다.
이 프로젝트는 좌석 수십~수백 개를 상태별로 색 구분해야 하고,
색약 사용자와 고대비 모드 대응이 필수인 접근성 요구사항이 있다.

## 검토한 선택지

- **CSS Modules**: 클래스명 자동 스코핑. CSS 문법 그대로. data 속성과 조합해 상태 스타일을 CSS 한 곳에 집중 가능.
- **Tailwind CSS**: 유틸리티 클래스 조합. 채용 공고에서 가장 많이 보이는 스택. 동적 상태 분기가 JSX 안에 흩어짐.
- **순수 CSS**: 별도 도구 없음. 클래스명 충돌을 직접 관리해야 함.

## 결정과 이유

**CSS Modules** 선택.

1. 좌석이 수백 개다. Tailwind면 유틸리티 클래스를 수백 번 반복하게 된다.
   CSS Modules는 클래스 하나 + data 속성으로 끝나고, 상태별 스타일은 CSS에서 처리할 수 있다.
   2차에서 좌석을 5,000개로 늘릴 때 클래스 문자열 크기가 성능에 영향을 주는지 측정해서 확인한다.
   지금은 가설이고, 측정 결과에 따라 이 근거의 유효성을 재검토한다.

2. 좌석 상태가 4가지이고 색으로 구분한다. 색약 사용자와 고대비 모드 대응을 위해
   CSS custom properties(`var(--color-*)`)로 색상 값을 관리하는 게 편하다.
   이런 스타일 설계를 CSS 한 곳에 모으고 싶다.

3. Tailwind는 상태별 조건부 클래스 분기가 JSX에 흩어진다.
   스타일 결정을 CSS 안에 집중시키는 방향을 택했다.

### 알고 선택한 단점

Tailwind가 채용 공고에 훨씬 많이 등장한다는 걸 알고 있다.
이 프로젝트의 특성(수백 개 좌석, 상태별 색 관리, 접근성)에 CSS Modules가 더 맞다고 판단했고,
Tailwind는 다음 프로젝트에서 직접 써서 보완할 계획이다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

- CSS 파일 간 값 중복이 늘어나고 디자인 토큰 관리가 손으로 안 되기 시작하면 재검토한다.
- 2차 측정에서 클래스 문자열 크기가 성능에 영향이 없다고 나오면, 근거 1번은 철회해야 한다.

## 되돌리는 비용

CSS Modules 파일이 컴포넌트와 1:1로 붙어 있어 파일 단위 교체가 가능하다.
다른 방식으로 전환 시 컴포넌트별로 순차적으로 마이그레이션할 수 있어,
전체를 한꺼번에 바꾸지 않아도 된다.
