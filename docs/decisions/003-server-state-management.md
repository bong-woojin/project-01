# 003. 서버 상태 관리 방식

> **미완결 — E~F단위에서 실제로 만난 문제를 채운 뒤 결론 확정**

## 상황

서버에서 가져오는 데이터(공연 목록, 좌석 상태, 예매 정보)를 어떻게 관리할지 결정해야 했다.
폴링이 포함되어 있고, 선점 성공 후 좌석 목록을 갱신하는 흐름도 있어
fetch 로직과 상태 관리가 얽히는 지점이 여러 군데 생긴다.

## 검토한 선택지

- **TanStack Query**: 폴링, 캐시 무효화, 로딩/에러 상태 추적 내장. 개념 학습 필요.
- **useEffect + fetch 직접 구현**: React 기본. 폴링·캐시 직접 관리. 반복 코드 많아짐.

## 지금까지의 판단 — 직접 구현으로 시작하는 이유

CSS Modules를 고른 것과 상황이 다르다.
CSS Modules는 멀쩡한 대체재였지만, 서버 상태 관리를 직접 짜는 건 대체가 아니라 그냥 없는 거다.
그리고 이 프로젝트의 핵심은 폴링 정리가 아니라 좌석 경합과 타입 설계다.

"왜 TanStack Query를 썼나"에 "많이 쓰니까요"라고 답하고 싶지 않다.
직접 겪은 문제를 근거로 말하고 싶다.

### 진행 순서

1. E~F단위에서 좌석 폴링을 먼저 `useEffect + fetch`로 직접 구현한다. **하루 저녁으로 제한.**
2. 그때 실제로 발생하는 문제를 그 순간에 기록한다.
3. 문제가 있었다면 TanStack Query로 전환하고 전환 근거를 이 문서에 채운다.
4. 문제가 없었다면 라이브러리 도입이 과했다는 것도 솔직하게 기록한다.

## 결정과 이유

*(E~F단위 작업 후 실제 발생한 문제를 토대로 채울 것)*

## 이 결정이 틀렸다면 어떻게 알 수 있나

직접 구현으로도 문제가 없었다면 라이브러리 도입은 과한 선택이었다는 뜻이다.
그 경우도 솔직하게 기록한다.

## 되돌리는 비용

TanStack Query 도입 전 단계(useEffect 구현)에서는 비용이 없다.
TanStack Query로 전환 후에는 `useQuery`, `useMutation` 훅이 컴포넌트에 직접 쓰이므로,
다시 걷어내려면 컴포넌트 전체를 수정해야 한다.
Supabase 호출을 별도 계층으로 감쌀지는 TanStack Query 도입 시점에 같이 판단한다.
