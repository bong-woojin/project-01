# 004. 폼 처리 방식과 필드 구성

## 상황

예매자 정보 입력 폼의 필드 구성과 구현 방식을 결정해야 했다.
로그인이 없는 구조라 입력받는 정보가 예매자를 식별하는 유일한 수단이 된다.

## 필드 구성 결정

### 받는 것
1. 예매자 이름 (필수)
2. 휴대폰 번호 (필수)
3. 개인정보 수집·이용 동의 체크박스 (필수)

### 안 받는 것과 이유

- **이메일**: 메일 발송 기능이 없다. 쓸 데가 없는 개인정보를 받는 건 잘못이다.
  2차에서 결제와 예매 확인 메일이 들어가면 그때 다시 판단한다.
- **동반자 수**: 선택한 좌석 수로 이미 결정된다. 중복 입력이다.
- **좌석 요청사항**: 좌석을 직접 고르는 앱이라 필요가 없다.

필드를 줄인 것도 판단이다. 수집하지 않은 이유를 남긴다.

## 폼 처리 방식 결정

**라이브러리 없이 직접 구현** (react-hook-form, zod 모두 미사용)

1. 필드가 3개다. react-hook-form을 도입할 근거가 약하다.
2. 이 폼의 진짜 어려움은 필드 검증이 아니다.
   선점 만료 타이머가 도는 중에 입력하고 제출하는 상황이다.
   입력 중 홀딩이 만료되면? 제출 순간 서버가 거절하면?
   폼 라이브러리는 이 문제를 해결해주지 않는다.
3. 에러 메시지를 스크린리더가 읽게 하고, 제출 실패 시 포커스를 옮기는 처리를
   직접 한다. 퍼블리셔 경험에서 잘 아는 영역이고 코드로 보여줄 수 있다.

zod도 미사용. 서버가 Postgres라 검증 스키마를 클라이언트와 공유할 수 없어서,
클라이언트에만 쓰는 스키마는 이 규모에 과하다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

필드가 늘어나거나 조건부 필드(선택에 따라 다른 필드가 나타나는 구조)가 생기면
직접 구현의 반복 코드가 쌓인다. 그 시점에 react-hook-form을 재검토한다.

## 되돌리는 비용

직접 구현한 폼 상태(`useState`)와 검증 로직을 react-hook-form으로 교체하려면
해당 컴포넌트를 통째로 다시 짜야 한다. 규모가 크지 않아 비용은 낮다.
