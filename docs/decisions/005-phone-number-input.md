# 005. 휴대폰 번호 입력 처리

## 상황

로그인이 없는 구조라 휴대폰 번호가 예매자 식별 수단이 된다.
오타가 나면 사전 안내 문자를 못 받는 문제가 생긴다.
SMS 인증은 소극장 규모에 과하다고 판단해 그 아래 선택지를 검토했다.

## 검토한 선택지

- 형식 검증만: 마찰 없음. 오타 감지 불가.
- 두 번 입력: 오타 발견 가능성 높아지지만 일관된 오타는 통과. 모바일 불편.
- 확인 화면 재표시: 자연스러운 흐름. 오타를 본인이 인식해야 함.
- 실시간 포맷팅 + 확인 화면: 입력 편의성과 시각적 확인을 결합.

## 결정과 이유

**문제 정의부터 바꿨다 — 오타 방지가 아니라 복구 경로 확보.**

번호가 유일한 신분증이라는 전제를 재검토했다.
관객은 현장에서 이름을 말하고, 주최자는 예매 목록에서 이름과 좌석으로 찾을 수 있다.
번호가 틀려도 입장은 된다. 실제 피해는 사전 안내 문자를 못 받는 정도다.
또한 `/bookings/:bookingId` URL 자체가 예매 확인서 역할을 한다. 번호와 무관하게 본인이 확인할 수 있다.

막을 수 없는 것을 막으려 하지 않고, 복구 가능하게 만드는 방향을 택했다.
이 판단의 근거는 소극장의 실제 운영 방식이다 — 현장에서 이름으로 확인한다.

### 구체적인 구현 방향

1. **`autoComplete="tel"` + `inputMode="numeric"`을 우선 적용한다.**
   비용이 거의 없고 효과가 가장 크다. 브라우저 저장 번호를 자동완성하면 타이핑 자체가 줄고,
   모바일에서 숫자 키패드가 뜨면 오타 확률이 낮아진다.

2. **포맷팅은 blur 시점에 한다. 실시간 포맷팅은 하지 않는다.**
   입력 중에 값을 바꾸면 커서 위치가 튄다. 중간 숫자를 지우고 다시 칠 때 커서가 끝으로 날아가는 문제가 생긴다.
   스크린리더에도 입력 중 값이 바뀌는 건 좋지 않다.
   이 판단을 남기는 이유: 커서 위치 문제는 실무에서도 자주 놓치는 부분이다.

3. **확인 화면에서 이름·번호·좌석을 함께 보여준다.** 발견 가능성만 높인다.

4. **예매 완료 화면에서 링크 저장·캡처를 안내한다.**
   `/bookings/:bookingId` 링크가 예매 확인서다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

- 2차에서 결제가 들어오면 번호가 환불 연락 수단이 되므로 중요도가 올라간다. 그 시점에 SMS 인증을 재검토한다.
- 주최자 화면에서 이름 검색이 불가능한 구조가 되면 "이름으로 현장 확인 가능"이라는 전제가 깨진다.

## 되돌리는 비용

두 번 입력 필드나 SMS 인증을 나중에 추가하더라도 폼 컴포넌트만 수정하면 된다.
blur 포맷팅 로직을 실시간으로 바꾸려면 커서 위치 처리 코드가 추가로 필요하다.
