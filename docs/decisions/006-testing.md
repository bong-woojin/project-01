# 006. 테스트 도구와 범위

## 상황

포트폴리오에서 테스트를 보여줄 필요가 있고,
이 프로젝트의 핵심 주장("동시 선점을 시스템이 막는다")을 코드로 증명해야 했다.

## 검토한 선택지

- **Vitest**: Vite 네이티브. 설정 부담 거의 없음. 단위/통합 테스트 가능.
- **Jest**: 가장 널리 쓰이지만 Vite 프로젝트에 추가 설정 필요.
- **React Testing Library**: 컴포넌트 테스트용. 1차에서는 UI 구조가 아직 흔들림.
- **Playwright**: E2E. 브라우저 2개 경합 시나리오에 적합하지만 2차로 미룸.

## 결정과 이유

**Vitest만 사용. 테스트 범위는 두 가지로 제한.**

Vite 프로젝트라 설정 부담이 거의 없다는 점이 첫 번째 이유다.

### 작성할 테스트 1 — 순수 함수 단위 테스트 (5~10개)

- 선점 만료 판정 함수
- 좌석 상태 도출 함수 (선점 정보 + 판매 정보 → 4가지 상태 중 하나)

경계 조건 중심: 정확히 만료 시각일 때, 만료 1초 전후.

**설계와 테스트의 일치:** 만료 판정 함수 안에서 `Date.now()`를 부르면 테스트를 쓸 수 없다.
시각을 인자로 받아야 테스트가 가능하다. 이 구조는 앞서 "만료 기준은 서버 시각"으로 정한 방향과 일치한다.
테스트하기 쉬운 구조가 곧 올바른 구조였다.

### 작성할 테스트 2 — 경합 통합 테스트 1개

같은 좌석에 선점 요청을 `Promise.all`로 동시에 두 번 보내서 하나만 성공하는지 확인한다.
테스트 실패 시에도 cleanup이 실행되도록 `try/finally` 구조로 작성한다.

이 테스트 하나가 이 프로젝트의 핵심 주장을 증명한다.

#### 테스트 데이터 격리 방식

별도 Supabase 프로젝트를 만드는 대신, DB에 테스트 전용 공연 데이터를 하나 만든다.
`concerts` 테이블에 `is_test: true` 컬럼을 두고, 경합 테스트는 그 공연의 좌석만 건드린다.

관객 화면에서 테스트 공연이 보이지 않도록 하는 방법:
- 공연 목록 조회 시 `is_test != true` 조건을 쿼리에 넣는다.
- 더 강하게 막으려면 Supabase RLS 정책에서 `anon` 롤이 `is_test = true`인 row를 SELECT하지 못하도록 설정한다.

**이 방식의 한계 (완전한 격리가 아닌 이유):**
- 테스트와 실제 앱이 같은 DB를 쓴다. 테스트 중 DB 장애가 생기면 실제 앱도 영향을 받는다.
- cleanup이 실패하면 테스트 좌석 데이터가 dev DB에 남는다.
- 테스트 공연 ID가 노출되면 누군가 그 공연의 좌석을 건드릴 수 있다 (1차에서는 사용자가 없어 사고 가능성 낮음).
- 완전한 격리는 별도 Supabase 프로젝트 또는 로컬 Supabase(Docker)가 필요하다. 1차에서는 그 비용을 감수하지 않는다.

### 안 하는 것과 이유

- **컴포넌트 테스트**: UI 구조가 아직 흔들리는 단계라 테스트를 계속 고치게 된다. 구조가 안정된 뒤에 한다.
- **E2E (브라우저 2개 경합)**: 2차로 미룬다. 대신 E단위에서 브라우저 창 두 개로 수동 재현하고 캡처해서 기록으로 남긴다.
- **커버리지 목표**: 세우지 않는다. 숫자를 채우려고 의미 없는 테스트를 쓰게 될 것 같다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

- 같은 버그가 두 번 이상 재발하는 영역이 생기면 그 부분에 테스트를 추가한다.
- 컴포넌트 리팩터링이 두려워지기 시작하면 컴포넌트 테스트 부재를 재검토한다.

## 되돌리는 비용

Vitest에서 Jest로 전환: 설정 파일 교체와 일부 API 차이 수정. 비용 낮음.
단위 테스트를 컴포넌트 테스트로 확장: 기존 테스트는 유지하고 추가하면 됨.
