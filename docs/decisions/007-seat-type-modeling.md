# 007. 좌석 상태 타입 모델링

## 상황

좌석은 4가지 상태를 가진다: 예매 가능 / 내가 선점 중 / 다른 사람이 선점 중 / 판매 완료.
이 상태를 TypeScript로 어떻게 표현하느냐에 따라 "불가능한 상태를 코드로 막을 수 있는지"가 달라진다.

## 검토한 선택지

- **boolean 플래그 조합**: `isHeld: true, isSold: true`가 동시에 가능. 현실에 없는 상태를 타입이 허용.
- **문자열 유니온**: 값이 하나라 두 상태가 동시에 존재 불가. 단순하고 읽기 쉬움.
- **Discriminated union**: 상태마다 가질 수 있는 필드가 다름. 불가능한 상태를 컴파일 타임에 차단.

## 결정과 이유

**Discriminated union** 선택.

`expiresAt`(선점 만료 시각)은 선점 중인 좌석에만 있어야 한다.
전체 좌석에 두면 `available` 좌석의 `expiresAt`이 무슨 의미인지 설명할 수 없다.

`held-by-other`에는 `expiresAt`을 넣지 않는다.
화면에 필요한 건 "잠겨 있다"는 사실뿐이고, 언제 풀리는지는 알려줄 필요가 없다.
알려주면 그 시각에 맞춰 대기하는 사람이 생길 수 있고,
앞서 "남의 선점 정보는 노출하지 않는다"는 판단과도 일관된다.

`held-by-me`와 `held-by-other`가 서로 다른 필드를 가지게 되어
discriminated union을 쓸 이유가 더 분명해졌다.

공통 필드(id, row, col 등)는 교차 타입(intersection)으로 분리했다.
유니온 안에서 4번 반복하지 않고, narrowing도 정상 동작한다.

### 세부 판단 기록

**판매 완료 판정이 선점 판정보다 먼저 온다.**
예매 확정 후에도 선점 기록을 남기기로 했다(이력 추적 목적).
`isSold`를 먼저 확인하지 않으면 판매된 좌석이 선점 중으로 보일 수 있다.

**`expiresAt <= now`면 만료된 것으로 본다.**
어느 쪽이든 최종 판정자는 서버이므로 클라이언트 판정은 표시 목적이다.
안전보다 일관성을 택했다. 조건을 하나로 고정해서 테스트로 못 박는 게 중요하다.

**`holderId`가 있고 `expiresAt`이 null이면 `held-by-other`로 취급한다.**
두 명이 같은 좌석을 잡는 것보다 한 명이 못 잡는 쪽이 낫다.

한계: 만료 시각이 없으므로 그 좌석은 자동으로 풀리지 않는다.
정상적인 흐름이면 이 상태는 발생하지 않아야 한다.
개발 환경(`import.meta.env.DEV`)에서 `console.warn`으로 경고를 남긴다.
운영 빌드 시 Vite가 이 코드를 제거하므로 사용자에게는 노출되지 않는다.

### 주의 — 상태는 시간이 지나면 스스로 바뀐다

서버가 `held-by-me`를 줬어도 만료 시각이 지나면 `available`이 되어야 한다.
서버 응답을 그대로 들고 있으면 화면이 거짓말을 하게 된다.
클라이언트에서도 만료 판정을 해야 할 수 있는데,
그러면 만료 판단 로직이 서버와 클라이언트 두 곳에 생긴다.
이 문제는 E단위 "선점 만료 시각 기준" 판단에서 다룬다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

상태가 4개를 넘어 늘어나거나(예: 예매 취소 대기), 상태별 필드 차이가 사라지면
문자열 유니온으로 단순화하는 걸 재검토한다.

## 되돌리는 비용

`Seat` 타입을 참조하는 컴포넌트와 함수를 모두 수정해야 한다.
타입 변경은 컴파일러가 영향 범위를 알려주므로 누락 없이 교체 가능하다.
